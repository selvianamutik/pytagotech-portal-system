## DEC-002: Package Manager — pnpm

- **Tanggal:** 2026-10-04
- **Terkait:** US-001

## DEC-003: Zona Waktu — Asia/Jakarta (WIB)

- **Tanggal:** 2026-10-04
- **Terkait:** FR-5, FR-26, US-037, US-038, US-024
- **Konteks:** PRD Bagian 8 menyebutkan "Zona waktu tunggal (WIB, Asia/Jakarta) untuk perhitungan SLA dan jadwal."
- **Keputusan:** Semua timestamp disimpan sebagai UTC di database Supabase. Konversi ke WIB (UTC+7) dilakukan di sisi server/client menggunakan `Intl.DateTimeFormat` atau library `date-fns-tz` dengan zona waktu `Asia/Jakarta`.
- **Alternatif yang dipertimbangkan:** Simpan sebagai WIB langsung, gunakan `moment-timezone`
- **Alasan:** Menyimpan UTC adalah praktik terbaik; konversi ke WIB hanya di tampilan dan kalkulasi SLA.
- **Konsekuensi:** Semua input tanggal/waktu dari user diasumsikan WIB dan dikonversi ke UTC sebelum disimpan.

## DEC-006: ID Format untuk Entitas
- **Tanggal:** 2026-10-04
- **Terkait:** US-028, US-031, FR-23
- **Konteks:** PRD menyebutkan format ID `MAT-xxxx` dan `PUB-xxxx` untuk content materials dan publications. Perlu konvensi untuk entitas lain.
- **Keputusan:**
  - Primary key semua tabel: UUID (generated by Supabase/Postgres)
  - Display ID (untuk ditampilkan ke user): sequence per entitas, misalnya `MAT-0001`, `PUB-0001`, `LEAD-001`, dst.
  - Display ID di-generate via Supabase trigger + sequence, bukan UUID
- **Alasan:** UUID cocok untuk relasi database; display ID pendek lebih user-friendly dan sesuai PRD.
- **Konsekuensi:** Setiap tabel entitas utama perlu kolom `display_id` dengan trigger auto-generate.

## DEC-010: Strategi Primary Key — UUID + Display ID Trigger

- **Tanggal:** 2026-10-05
- **Terkait:** Semua US/FR (Fase 2)
- **Konteks:** AGENT_RULES mewajibkan satu strategi PK konsisten (Fase 2 Langkah 3).
- **Keputusan:** PK semua tabel = UUID v4 (`gen_random_uuid()`); ID ramah-user (`LEAD-xxx`, `MAT-xxxx`, …) sebagai kolom `display_id TEXT UNIQUE` yang diisi trigger + sequence (meneruskan DEC-006).
- **Alternatif yang dipertimbangkan:** BIGINT auto-increment sebagai PK (lebih hemat, tapi bocor urutan dan tidak cocok untuk RLS multi-tenant di masa depan); display ID sebagai PK (rapuh terhadap perubahan format).
- **Alasan:** UUID aman untuk relasi terdistribusi dan tidak menebak; display ID tetap pendek untuk UI sesuai PRD.
- **Konsekuensi:** Semua FK bertipe UUID; migration Fase 3 wajib memakai tipe ini.

## DEC-014: Wiring Supabase Auth — Service Tetap, Route Handler untuk Admin

- **Tanggal:** 2026-10-05
- **Terkait:** US-002, FR-1
- **Konteks:** Swap mock → Supabase Auth nyata adalah prasyarat semua service swap (policy RLS `to authenticated`; mock auth = anon = 0 baris).
- **Keputusan:**
  - `services/auth.ts` memakai browser client; signature + `ServiceResult` dipertahankan sehingga komponen/store tak berubah (kecuali teks bantuan Fase 1).

- **Alasan:** Satu lapis service, secrets hanya di server, alur sesuai kontrak UI Fase 1.
- **Konsekuensi:** Butuh `SUPABASE_SERVICE_ROLE_KEY` di server + user Super Admin pertama dibuat via Dashboard/SQL (terdokumentasi di `API.md`); `db reset` di mesin Docker tetap wajib sebelum klaim DONE.

## DEC-015: Master Data Terpusat — Satu Tabel Opsi, Fallback Hook, Tim/PIC Tanpa Flag Aktif

> **Diperbarui 2026-10-27:** bagian tim/PIC dan fallback `listLeadPICs()` di bawah sudah digantikan **DEC-018** (Q-015/CR-004). `team_members` kini punya `is_active`; dropdown memfilter anggota aktif, dan fallback mock hanya dipakai saat query gagal, bukan saat tabel kosong.

- **Tanggal:** 2026-10-27
- **Terkait:** US-005, FR-3
- **Konteks:** Sembilan kelompok dropdown masih hardcode di konstanta form. Skema sudah menyediakan `master_options(category, value, is_active)` dengan RLS (user biasa hanya melihat opsi aktif) dan `team_members`, tetapi `team_members` belum punya kolom `is_active`.
- **Keputusan:**
  - Delapan kategori memakai satu tabel `master_options` (bukan satu tabel per dropdown): `industry`, `lead_status`, `interest_stage`, `brand`, `platform`, `pillar`, `feature_category`, `priority`. Halaman `/pengaturan/master-data` (Super Admin) melakukan CRUD + aktif/nonaktif.
  - Rename dan hapus opsi ditolak bila opsi sudah direferensikan tabel lain (FK komposit tanpa `ON UPDATE CASCADE`, dan `ON DELETE` default `NO ACTION`). Jalur yang disarankan: nonaktifkan opsi lama, tambah nilai baru. Service tetap mengecek referensi lebih dulu agar pesan error jelas.
  - Form membaca opsi lewat hook `useMasterOptions()`: satu kali baca saat mount, fallback ke konstanta lama bila query gagal atau tabel kosong. Tujuannya agar demo tetap berjalan sebelum sesi/database siap tanpa mengorbankan sumber data utama.
  - `team_members` memakai CRUD + guard hapus berbasis 19 kolom referensi. Tidak ada tombol nonaktifkan karena skema belum mendukung; keputusan penambahan flag menunggu Q-015/CR.
  - `listLeadPICs()` membaca `team_members` dan hanya jatuh ke mock user bila tabel belum bisa dibaca/kosong.
- **Alternatif yang dipertimbangkan:** Satu tabel per dropdown (ditolak — duplikasi RLS/halaman/service); filter `is_active` di client setelah membaca semua baris (ditolak — RLS sudah menyembunyikan nonaktif untuk user biasa); menambah `team_members.is_active` sekarang (ditolak sementara — butuh CR + migration dan verifikasi DB belum tersedia).
- **Alasan:** Satu kontrak tipe/service untuk semua dropdown, perubahan opsi langsung terlihat di form, dan tidak ada perubahan skema tanpa persetujuan.
- **Konsekuensi:** Service modul yang masih mock (lead/interest/feature/sosmed) tetap memvalidasi nilai terhadap konstanta lama saat menyimpan, sehingga opsi baru bisa tampil di dropdown tetapi ditolak service sampai modul tersebut dimigrasikan ke Supabase. Verifikasi hapus-terjaga memakai query referensi per tabel; tabel referensi harus cocok dengan skema (sudah divalidasi terhadap `20261005000000_initial_schema.sql`). Penghapusan memakai `.delete().select(...)`; 0 baris dianggap gagal agar RLS yang menyaring DELETE tidak tampil sebagai sukses. Cek referensi dijalankan paralel (`Promise.all`) agar 19 query tim/PIC tidak berurutan.

## DEC-017 - RLS `leads`/`projects` Tetap Role-Based (Q-019/CR-003)

- **Terkait:** US-003, US-009, US-020 / FR-1, FR-6, FR-15

## DEC-018 - Status Aktif Tim/PIC via `team_members.is_active` (Q-015/CR-004)

- **Tanggal:** 2026-10-27
- **Terkait:** US-005, US-022 / FR-3
- **Konteks:** AC3 US-005 meminta opsi yang dipakai hanya dinonaktifkan. `master_options` sudah punya `is_active`, tetapi `team_members` belum. Menghapus anggota yang direferensikan akan membuat FK `ON DELETE SET NULL` menghapus jejak PIC/PM/assignee lama.
- **Keputusan:** Pemilik memilih opsi A (Q-015): tambah `team_members.is_active boolean NOT NULL DEFAULT true` lewat CR-004 + migration `20261027000000_team_members_is_active.sql`. Semua anggota tetap bisa dibaca user terautentikasi (policy SELECT tidak diubah) agar nama historis resolve; service dropdown memakai `listActiveTeamMembers()` yang memfilter `is_active = true`. - **Konsekuensi:** Form/dropdown hanya menampilkan anggota aktif; halaman pengelolaan menampilkan semua dengan badge Aktif/Nonaktif. Migration sudah diterapkan ke live dan diverifikasi via REST + browser pada 2026-10-27.

## DEC-019 - Perbaikan Policy DELETE `master_options` (Q-016)

- **Tanggal:** 2026-10-27
- **Terkait:** US-005, US-003 / FR-3, FR-1
- **Konteks:** DELETE `master_options` oleh Super Admin di live mengembalikan `200 []`, sedangkan INSERT/UPDATE dan DELETE `team_members` berhasil. Service role berhasil, sehingga kegagalan berada di policy/grant role `authenticated`, bukan di kode service.
- **Keputusan:** Pemilik memilih opsi A (Q-016): perbaiki live + migration pengaman. - **Alasan:** RLS tetap menjadi lapisan otorisasi; grant role tidak memperluas akses karena policy membatasi ke Super Admin.
- **Konsekuensi:** Policy live sudah diperbarui dan diverifikasi via REST + browser pada 2026-10-27; data uji dibersihkan. Migration ini juga menjaga hasil `db reset` tetap konsisten.
