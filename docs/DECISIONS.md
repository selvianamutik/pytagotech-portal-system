## DEC-001: Stack Utama — Next.js + Supabase + shadcn/ui + Tailwind

- **Tanggal:** 2026-10-04
- **Terkait:** US-001, FR-1, FR-2
- **Konteks:** PRD secara eksplisit menentukan stack di bagian "Technical Considerations" (Bagian 8).
- **Keputusan:** Menggunakan stack sesuai PRD: Next.js (App Router, TypeScript), Supabase (Postgres, Auth, Storage, Realtime, RLS), shadcn/ui, Tailwind CSS.
- **Alternatif yang dipertimbangkan:** Tidak ada — PRD telah menentukan.
- **Alasan:** Mengikuti PRD adalah kewajiban per AGENT_RULES.md Bagian 2.
- **Konsekuensi:** Semua komponen UI harus menggunakan shadcn/ui; semua query database via Supabase JS Client.

## DEC-002: Package Manager — pnpm

- **Tanggal:** 2026-10-04
- **Terkait:** US-001
- **Konteks:** PRD tidak menentukan package manager. Perlu satu pilihan yang dikunci.
- **Keputusan:** pnpm
- **Alternatif yang dipertimbangkan:** npm, yarn, bun
- **Alasan:** pnpm lebih cepat dari npm, lebih deterministic (symlink store), dan lebih umum di project Next.js modern. Lockfile `pnpm-lock.yaml` di-commit.
- **Konsekuensi:** Semua developer harus install pnpm >= 9. CI/CD menggunakan pnpm.

## DEC-003: Zona Waktu — Asia/Jakarta (WIB)

- **Tanggal:** 2026-10-04
- **Terkait:** FR-5, FR-26, US-037, US-038, US-024
- **Konteks:** PRD Bagian 8 menyebutkan "Zona waktu tunggal (WIB, Asia/Jakarta) untuk perhitungan SLA dan jadwal."
- **Keputusan:** Semua timestamp disimpan sebagai UTC di database Supabase. Konversi ke WIB (UTC+7) dilakukan di sisi server/client menggunakan `Intl.DateTimeFormat` atau library `date-fns-tz` dengan zona waktu `Asia/Jakarta`.
- **Alternatif yang dipertimbangkan:** Simpan sebagai WIB langsung, gunakan `moment-timezone`
- **Alasan:** Menyimpan UTC adalah praktik terbaik; konversi ke WIB hanya di tampilan dan kalkulasi SLA.
- **Konsekuensi:** Semua input tanggal/waktu dari user diasumsikan WIB dan dikonversi ke UTC sebelum disimpan.

## DEC-004: Struktur Folder Frontend

- **Tanggal:** 2026-10-04
- **Terkait:** US-001
- **Konteks:** Next.js App Router memberi kebebasan struktur. Perlu konvensi yang konsisten.
- **Keputusan:**
  ```
  frontend/
  ├── src/
  │   ├── app/              # Next.js App Router pages & layouts
  │   ├── components/       # Komponen UI reusable
  │   │   ├── ui/           # shadcn/ui base components
  │   │   └── [feature]/    # Komponen per fitur
  │   ├── lib/              # Utilities, helpers, Supabase client
  │   ├── services/         # Lapisan pemanggilan data (mock & API)
  │   ├── mocks/            # Data mock untuk Fase 1 (Frontend)
  │   ├── types/            # TypeScript types/interfaces (kontrak data)
  │   ├── hooks/            # Custom React hooks
  │   └── store/            # State management global (Zustand)
  └── ...
  ```
- **Alasan:** Memisahkan `services/` dari komponen agar mock mudah diganti API nyata di Fase 2 (sesuai AGENT_RULES.md Fase 1).
- **Konsekuensi:** Komponen TIDAK BOLEH memanggil fetch atau mock langsung — hanya via `services/`.

## DEC-005: State Management — Zustand

- **Tanggal:** 2026-10-04
- **Terkait:** US-001, US-002
- **Konteks:** PRD tidak menentukan state management library. Perlu pilihan untuk state global (user session, filter, notifikasi).
- **Keputusan:** Zustand untuk state global client-side. Server state (data fetching) menggunakan React Server Components + Supabase.
- **Alternatif yang dipertimbangkan:** Redux Toolkit, Jotai, Context API, Tanstack Query
- **Alasan:** Zustand ringan, tidak membutuhkan boilerplate besar, kompatibel dengan Next.js App Router. Tanstack Query dipertimbangkan untuk caching server state jika dibutuhkan (dicatat sebagai CR jika perlu).
- **Konsekuensi:** Tim mengikuti pola store Zustand yang sama di semua fitur.

## DEC-006: ID Format untuk Entitas

- **Tanggal:** 2026-10-04
- **Terkait:** US-028, US-031, FR-23
- **Konteks:** PRD menyebutkan format ID `MAT-xxxx` dan `PUB-xxxx` untuk content materials dan publications. Perlu konvensi untuk entitas lain.
- **Keputusan:**
  - Primary key semua tabel: UUID (generated by Supabase/Postgres)
  - Display ID (untuk ditampilkan ke user): sequence per entitas, misalnya `MAT-0001`, `PUB-0001`, `LEAD-001`, dst.
  - Display ID di-generate via Supabase trigger + sequence, bukan UUID
- **Alasan:** UUID cocok untuk relasi database; display ID pendek lebih user-friendly dan sesuai PRD.
- **Konsekuensi:** Setiap tabel entitas utama perlu kolom `display_id` dengan trigger auto-generate.
